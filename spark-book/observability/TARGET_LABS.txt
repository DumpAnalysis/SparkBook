# 91  Prometheus and Grafana for GPU observability

This chapter turns the earlier GPU sampler and inference-server metric captures into a running monitoring laboratory. An exporter collects mapped-driver observations inside WSL2. Prometheus scrapes and retains time series, evaluates recording rules and alerts, and exposes a query API. Grafana queries Prometheus through a provisioned data source. The companion supplies every program, configuration generator, dashboard, rule test and command capture used here.

The example remains a 64 GB unified-memory RTX Spark laptop with approximately 30 GB reported to the GPU. Read the actual device total; do not hard-code 30 GB as an allocation ceiling or add it to the host's 64 GB. Prometheus and Grafana use CPU and host memory. They neither increase the GPU allocation budget nor make missing driver counters available.

Evidence boundary. Preparation ran native Linux amd64 binaries on a CPU-only system. Prometheus collection, queries and alert transitions were executed against explicitly SIMULATED GPU readings. Grafana's database, data-source registration and dashboard provisioning were checked. Its query backend was unavailable because the preparation sandbox denied the plugin's Unix socket. Dashboard rendering and live WSL2, ARM64, GPU, Docker and Kubernetes operation remain target qualification steps. A successful provisioning check alone is not a working dashboard. The independent review outcome is recorded in Exercise 214 and Appendix E.

## Choose the collection path deliberately

Keep the existing Windows NVIDIA driver mapped into WSL2. This chapter installs no Linux display driver. The live exporter invokes the guest-visible nvidia-smi, using /usr/lib/wsl/lib/nvidia-smi if necessary. NVIDIA documents limited NVML functionality in WSL, including unavailable utilization and active-process queries. Individual fields must therefore be tested; CUDA execution can work while a monitoring field does not. [186]

DCGM Exporter is valuable for supported NVIDIA deployments, but the DCGM support statement describes bare-metal and full-passthrough environments. That is not evidence that this WSL2 laptop supports DCGM. Do not start a privileged DCGM container merely to obtain a green dashboard. If a future driver/platform combination documents support, retain the exact matrix, versions and a field-by-field comparison before substituting it for this collector. The default exercises use no DCGM dependency. [187, 188]

The live exporter queries ten fields independently: GPU busy percentage, memory-controller busy percentage, device memory used/free/total, temperature, power draw/limit and SM/memory clocks. Memory-controller busy time is not the percentage of device memory occupied. The exporter converts MiB to bytes, MHz to hertz and percentages to fractions. Unsupported, malformed, timed-out and stale readings omit the corresponding measurement gauge and retain an explicit availability/status series. A real zero remains a measurement.

The HTTP endpoint serves a cached snapshot. Scraping it does not initiate a fresh driver query. The collector polls every five seconds by default, bounds each query to one second, and keeps four rotating raw-log files of at most approximately 1 MiB each. One slow poll can exceed five seconds because fields are queried separately. Poll duration and age are therefore observable. After sixty seconds without a completed poll, measurement gauges disappear and field status becomes stale.

## Exercise 216  Read rates, histograms and latency correctly

Goal: distinguish an instantaneous gauge, a cumulative counter and a distribution. With the fixture stack running, drive the synthetic HTTP workload. These requests execute a bounded CPU sleep; no language model, CUDA kernel or inference engine runs.

```

python3 observability/client.py work \

  --count 20 --delay-ms 20 --errors 2

python3 observability/client.py query \

  'sum(rate(lab_demo_requests_total[1m]))'

python3 observability/client.py query \

  'sum(lab_demo_requests_total)'

```

The complete driver transcript above records 18 HTTP 200 responses and two intentionally generated 503 responses. The count is 20; request rate depends on the observation window. Wait for several scrapes before reading a rate. Repeat with a 100 ms delay and compare the latency panels over a time range that includes both phases. Do not label the injected error fraction as a model-quality measure.

The following PromQL expression estimates p95 from cumulative classic histogram buckets. Take rate before aggregating, preserve the le bucket boundary and choose a window with enough observations. The histogram has finite buckets from 5 ms through one second plus +Inf. An interpolated percentile is not an exact percentile of raw requests. An empty or zero-request window can produce no result or NaN; do not conceal it with a fabricated zero. [194, 195]

```

histogram_quantile(

  0.95,

  sum by(le)(

    rate(lab_demo_request_duration_seconds_bucket[1m])

  )

)

```


With all 20 observations in the (10 ms, 25 ms] bucket, linear interpolation gives 0.01 + 0.95 × 0.015 = 0.02425 s regardless of their exact positions within that bucket; an identical p95 in another run need not mean identical request latencies. To compute mean latency, divide the rate of the duration sum by the rate of the duration count. To inspect restarts, use resets(lab_demo_requests_total[5m]); counters restart at zero while gauges may legitimately rise or fall. Do not use rate on temperature or memory-used gauges. [194]

The companion queries.txt supplies copyable expressions for GPU bytes, availability, scrape duration, collector age, active series, request rate, error fraction and model-serving metrics. Keep request IDs, prompts, filenames and arbitrary user text out of metric labels. Store those details in bounded logs or traces, then correlate by time and a separately retained run identifier. Labels create new time series; the teaching exporter uses one UUID, a bounded source set, ten field names and a small status set.

## Exercise 217  Test alert transitions and missing evidence

Goal: tell an unhealthy device observation from a broken monitoring path. rules.yml defines one recording rule and five alerts. GpuMemoryPressure requires a ratio above 0.90 for twenty seconds. GpuBusyCounterUnavailable holds for twenty seconds. GpuExporterDown requires up=0 for fifteen seconds. GpuJobMissing detects an absent GPU job over thirty seconds. GpuCollectorStale detects a poll timestamp older than sixty seconds while the scrape remains up, with a ten-second hold. These are teaching thresholds, not hardware safety limits. [196]

Resolve the promtool path from the receipt and run the six deterministic rule scenarios. They check pending/firing/resolved pressure, unavailable versus zero, down versus absent, stale producer and an invalid memory denominator.

```

  "$HOME/spark-observability-tools/tools.json")

cd observability

"$PROMTOOL" check rules rules.yml

"$PROMTOOL" test rules rules-test.yml

cd ..


```

Prometheus evaluates the for duration across rule evaluations. An expression becoming true normally enters pending before firing; one sample is not enough to satisfy a hold. Rule tests use a deterministic synthetic timeline, while the integration driver waits on actual API states. Neither sends a message or page. Prometheus alert evaluation is not notification delivery; Alertmanager routing and external receivers are intentionally outside this local exercise. [196, 197]

With the interactive stack running, inject each case and inspect http://127.0.0.1:9090/alerts and the retained API response. Allow at least thirty seconds per phase for collection plus the hold interval.


Repeat with missing, malformed and zero. For a missing busy field, up remains one, availability becomes zero and busy disappears. For a valid zero, availability remains one and busy equals zero. A stopped exporter is different: up becomes zero. A removed scrape job is different again: eventually no up series remains. The stale-producer rule protects against a responsive HTTP endpoint that serves an old cache. Unit tests cover the latter cases without suspending or killing unrelated laptop processes.

## Retention, debugging and recommendations

Start with native tools, five-second collection and one GPU UUID. Keep the driver/platform capability record beside the dashboard. Use the device-reported total for device occupancy, and the earlier host-memory exercises for unified-memory pressure. Do not infer per-process GPU memory, ECC health, Xid events, SM occupancy or Tensor Core activity from this ten-field exporter. Unsupported fields require other qualified evidence.

The supplied Prometheus retention settings are 24 hours and 500 MiB of retained blocks. The size setting is not a strict cap on all directory contents: the head/WAL and other files need additional disk space. Check disk use, series counts, scrape duration and process resident memory during longer runs. Keep Prometheus local; authentication, TLS, long-term storage and external alert routing would be separate deployment work. [202]

Debug in dependency order: driver field response; exporter raw snapshot; /metrics; Prometheus target health and last error; query labels/time range; Grafana data-source health; panel query and unit. If Prometheus has data but Grafana fails, inspect the plugin and data-source logs before changing the GPU workload. If only one field is absent, do not restart the whole stack as the first diagnosis. If every field disappears while up stays one, inspect collector age and raw query failures.

The resulting evidence package should include exact binaries/images, capability results, configuration, raw observations, API responses, alert transitions, a source-labelled screenshot and the workload transcript. Keep secrets and model inputs out of that package unless deliberately required. This provides a repeatable monitoring laboratory while leaving kernel-level attribution to the book's tracing and CUDA debugging tools.
