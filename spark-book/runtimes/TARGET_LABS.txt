97  Ollama as a local model owner
Ollama adds a model manager and HTTP service to the laboratory. It is useful when several clients need one resident model, but a convenient model name can conceal changes in weights, templates or backend placement. We will preserve those identities, exercise the wire protocol, and connect server observations to the monitoring work in Chapter 91. Unsloth in Chapter 98 changes model weights; LM Studio in Chapter 99 supplies another local service; Nemotron in Chapter 100 is a model family. These are different components of a deployment.
The example remains the owner's 64 GB RTX Spark laptop with about 30 GB reported for the GPU. All execution below belongs inside WSL2. The Windows NVIDIA driver is already exposed to Linux. Installing Ollama is not a reason to install a Linux display driver. CUDA 13.4 reported by the owner does not identify the CUDA libraries embedded in every inference binary. Retain the toolkit, driver, backend and executable identities separately.
The companion runtimes/ directory contains sixteen standard-library CPU controls, their complete captures, bounded clients, selective downloaders and target training scripts. Run commands from spark-book/. EXECUTED controls use fabricated model responses or catalog metadata and do not run Ollama, Unsloth, LM Studio or Nemotron. TARGET PROCEDURE blocks require your WSL2 results. No successful GPU output has been invented. Use a fresh output path on each run.

98  Unsloth adaptation with measurable training boundaries
Unsloth offers optimized loading and adaptation paths. In this chapter it is a candidate implementation of the adapter-training experiment, with the same obligations as any other stack: a native installation, a frozen base model, separated evaluation data, finite updates, recoverable checkpoints and measured memory. Package installation alone is insufficient evidence of any of these properties.
Use a separate environment. Unsloth's WSL instructions and requirements identify dependencies including PyTorch, Triton and quantized-loading components; their native support must be checked for the actual ARM64 Linux and GPU combination. The publisher's DGX Spark recipes concern different hardware and cannot establish compatibility with this 64 GB WSL2 laptop. Neither a local CUDA 13.4 toolkit nor an x86-64 success proves that the required ARM64 wheels or kernels exist. [235, 236]

99  LM Studio inside WSL2 with a headless service
This chapter uses LM Studio's Linux headless core, llmster, and its lms command-line tool. The graphical Windows application is not part of the execution path. The official requirements list Linux x64 and ARM64 distributions, but the local CPU architecture, selected inference runtime and WSL2 GPU path still require qualification. 100  Nemotron models beyond the GPU weight budget
Nemotron is NVIDIA's model family, distinct from the NeMo training and deployment framework. This laboratory selects NVIDIA-Nemotron-3-Nano-30B-A3B as a concrete example. Its hybrid Mamba-2, attention and mixture-of-experts design has about 30 billion total parameters and 3.5 billion active parameters per token. The governing terms are the NVIDIA Nemotron Open Model License. The active count concerns selected computation; the stored model still contains the other experts. [249]
We use a pinned ggml-org GGUF conversion and preserve its identity separately from NVIDIA's upstream model. The retained revision matched the repository's main revision on 28 October 2026; main can advance, so later agreement is not assumed. Format support and native execution require separate checks. The Q4, Q8 and BF16 files have different storage requirements. A model-family name, active-parameter count or maximum context is not a memory admission rule. [250]
