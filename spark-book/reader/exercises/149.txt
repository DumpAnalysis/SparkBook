Exercise 149  Diagnose vLLM concurrency and deploy the qualified owner

Question
How do concurrent vLLM requests behave before and after moving the owner into the cluster?

Technology background

vLLM and serving language models

vLLM is an inference engine and server for language models. It schedules generation for active requests and manages memory used by their attention caches. Continuous batching lets the set of active sequences change as requests arrive or finish. A compatible HTTP API lets the lab use a familiar client.

Qualify the chosen image, model and device together. Check the server’s ready model identity, make one bounded generation request, then raise concurrency. Separate time in the queue, time to first content and completion. More available weight memory alone does not determine the number of concurrent sequences it can serve.

Dynamic batching and bounded admission

A batch groups compatible inputs into one model operation. Dynamic batching collects requests that arrive separately and can briefly wait for more work before dispatch. This can improve throughput while increasing the wait for an individual request. A bounded queue limits how much pending work the server admits.

Give every request its own ID. On overload, follow it from submission to rejection, cancellation or exactly one completed response. Compare queue time with model execution time. A request that timed out at the client may still occupy the server until cancellation reaches the owner.

Kubernetes, K3s, Pods and Services

Kubernetes runs workloads from a declared desired state. K3s is the Kubernetes distribution used for the local cluster. A Pod runs one or more containers together. A Deployment manages replicas and replacements. A Service gives clients an address that can route requests to matching ready Pods. kubectl is the command-line client.

Follow the chain from Deployment to Pod to ready endpoint and, finally, one inference reply. If a rollout stalls, inspect the Pod’s events, logs and readiness check. A created Deployment confirms that Kubernetes accepted the description; the request tests whether the model can serve.

Run in your lab
Use the Docker owner, pinned image and model directory from Exercise 148. After the Docker measurement, release the GPU and run the K3s commands on the qualified lab cluster. The generated manifest supplies the WSL driver bootstrap, writable caches, a 1 GiB KV cache and GPU utilization 0.12. The reader’s pod returned two HTTP 200 replies as UID 10001.

: "${LAB_RUN:?Run source reader/new_run.sh first}"

python serving/client.py chat-load --base http://127.0.0.1:8000 --model local-model --requests 8 --concurrency 2 --out "$LAB_RUN/vllm-load"
# Complete the Docker comparison and stop your Exercise 148 GPU owner.
docker logs spark-vllm > "$LAB_RUN/vllm-docker.log" 2>&1
docker stop spark-vllm
: "${VLLM_IMAGE:?Export the same qualified repository digest used in Exercise 148}"
: "${MODEL_DIR:?Export the absolute model directory used in Exercise 148}"
python serving/deploy.py vllm --image "$VLLM_IMAGE" --model-dir "$MODEL_DIR" --gpu --out "$LAB_RUN/vllm.yaml"
kubectl apply -f "$LAB_RUN/vllm.yaml"
kubectl -n spark-lab rollout status deployment/spark-vllm --timeout=900s
(
  kubectl -n spark-lab port-forward --address 127.0.0.1 service/spark-vllm 18000:8000 > "$LAB_RUN/vllm-forward.log" 2>&1 &
  forward_pid=$!
  trap 'kill "$forward_pid" 2>/dev/null || true' EXIT
  curl -fsS --retry 12 --retry-connrefused --retry-delay 1 http://127.0.0.1:18000/health &&
  python serving/client.py chat-load --base http://127.0.0.1:18000 --model local-model --requests 2 --concurrency 1 --out "$LAB_RUN/vllm-k3s"
)
kubectl -n spark-lab logs deployment/spark-vllm > "$LAB_RUN/vllm-pod.log"

Interpret the result

Finish
