72  Inference services and request diagnostics

A model becomes a service when callers depend on its request contract, readiness, response identity and failure behavior. We carry Chapter 71’s single-owner design into an HTTP service, then use the same client evidence discipline for llama.cpp, vLLM and NVIDIA Triton Inference Server. The latter is a model-serving system; it is distinct from the Triton GPU kernel language.

All new files are in serving/. The live HTTP controls below were EXECUTED on x86-64 Linux with Python 3.12.14 and NumPy 2.3.5. They use the small offline embedding fixture from Chapter 71 on the CPU. The container, Kubernetes, vLLM and Triton deployment commands are TARGET procedures for the ARM64 WSL2 laptop. Their success is not inferred from these controls. Full driver transcripts, response bodies, structured server logs and generated repositories are included.

The laptop remains a 64 GB unified-memory system with about 30 GB reported for the GPU. A container or pod creates no additional physical memory. Keep the existing Windows NVIDIA driver mapping into WSL2. The reported CUDA 13.4 installation is a separate observation from the runtime inside a serving image. A successful native CUDA program, an ARM64 image pull and an actual container model inference are three different qualification steps.

Exercise 136 Establish an inference API contract

server.py runs one NumPy inference executor behind a local HTTP endpoint. Admission is limited to two outstanding inference requests; transport threads are limited separately to sixteen. Input contains one to four strings, each one to sixteen UTF-8 bytes, and the JSON body is limited to 4,096 bytes. This deliberately small contract makes rejection behavior easy to reproduce. The byte tokenizer, padded mean pooling and fixed weights are diagnostic controls, not a useful sentence encoder.

The response preserves input order and returns sixty-four float32 values per input, the model name and a weight revision. Valid request IDs are echoed. Unknown models return 404, invalid inputs 400 and oversized bodies 413. The retained numerical result is compared with the separately expressed Chapter 71 oracle. A 200 response alone is insufficient: inspect shape, ordering, revision and values.


For manual interaction, start the server in one WSL terminal and use the client in another. All run directories must be new. The service implements a small OpenAI-shaped embeddings contract; this does not claim complete OpenAI API compatibility. No external API account is needed.

python -m pip install -r serving/requirements.txt

python serving/server.py --port 8088

python serving/client.py embed --out runs/http-one

curl --fail http://127.0.0.1:8088/v1/models

curl --fail http://127.0.0.1:8088/metrics

To substitute a trained sentence encoder from Chapters 49–56, preserve its actual tokenizer, attention mask, pooling, normalization, model revision and dimensionality. Run a local-versus-service vector comparison and a held-out retrieval test before changing the API’s model identity. The fixture’s byte tokenizer and sixty-four dimensions must not silently stand in for BERT or a fine-tuned embedding model.

Exercise 137 Separate liveness readiness and draining

The lifecycle control delays loading, sends a request after warmup, then terminates the process while that request is admitted. A second process injects a load failure. Liveness answers whether the process can respond; readiness answers whether it should receive inference requests. A load failure remains visible as live but unready. The admitted request finishes before the normal process exits.


SIGTERM first changes the service phase to draining and stops accepting new sockets. Existing handlers and the single executor are joined. The outer control bounds shutdown to ten seconds; the deployment examples allow thirty seconds. There is no active-kernel cancellation API. A client timeout does not prove that computation stopped, and a request ID is not an idempotency implementation. Retrying an agent action or training update requires the stronger commit protocol discussed in Chapter 71.

Exercise 138 Observe overload and queue delay

Eight clients enter together while the CPU owner has an injected 100 ms delay per inference. Two requests are admitted and six receive 429 with Retry-After. Complete bodies and every status are retained, including errors. This experiment tests the capacity contract; its latency and throughput are not GPU or laptop performance measurements.


Join the accepted request IDs with accepted_ns, start_ns and end_ns in server.jsonl. Queue time is owner-start minus admission; inference time includes the injected delay. HTTP latency also includes parsing, serialization and transport. The metrics use bounded route/status labels, with request IDs kept in logs rather than metric labels. A transport-capacity rejection occurs before the application handler and is not included in its counters; client outcomes therefore remain the end-to-end record.

python serving/client.py load --requests 64 \

  --concurrency 2 --out runs/http-load-2

python serving/client.py load --requests 64 \

  --concurrency 4 --out runs/http-load-4

Compare all status counts, successful request rate and successful latency together. The client uses a closed loop with a bounded thread pool. It does not represent an independent arrival process, and rejected requests are excluded from success-latency quantiles. Use longer repeated runs after warmup for a target SLO; a sixteen-request p95 is only a diagnostic sample. For open-loop testing, additionally retain offered arrival times and shed load rather than allowing an unbounded generator queue.

Exercise 139 Measure generation streaming correctly

The parser control contains a heartbeat, a role-only event, two content events and a terminal marker. It tests parsing only. The target client records time to first nonempty content delta, all received events and total completion time. A content delta can contain multiple tokens, so this is first-content latency, not a claim about a tokenizer’s first token. A missing terminal marker is retained as incomplete.

Exercise 150 Build and serve a versioned Triton embedding model

The companion creates lab_embedding/config.pbtxt, a numeric version directory 1, model.py and weights.npz. Configuration fixes the input TOKENS to INT64 with sixteen elements per sample and the output EMBEDDINGS to FP32 with sixty-four values. max_batch_size is eight; one KIND_CPU instance is selected. The Python backend receives a list of inference requests. Our execute implementation explicitly concatenates their input batches, makes one vectorized NumPy call and splits the results back into original request sizes. That behavior is tested with a lightweight API double using unequal batch sizes. This is an executed Python logic test, not execution of Triton’s scheduler, HTTP protocol or backend process. [117]
